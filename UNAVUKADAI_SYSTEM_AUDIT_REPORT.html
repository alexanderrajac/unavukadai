2. Do You Need a Database? (Architectural Decision)

DECISION: YES — A DATABASE IS MANDATORY
The bugs you are experiencing (orders missing, rider location dropping or showing in the wrong place) are direct consequences of using db.json and volatile Node.js in-memory variables.

Here is why the current architecture causes failures:

  • Rider Coordinates are In-Memory Only: In server/index.js line 135, coordinates are stored in let riderLocations = {}. Every time Node restarts, crashes, or reloads, all live rider positions are instantly deleted.
  • Race Conditions in File Writes: If a customer places an order while a restaurant accepts another order, multiple concurrent calls to fs.writeFileSync('server/data/db.json') run simultaneously. One write overwrites the other, causing orders to disappear.
  • No Geospatial Searching: Delivery platforms require finding nearest riders within 3–5 km. A database with spatial indexing (PostGIS or MongoDB 2dsphere) can calculate this in 1 millisecond.

3. Rider Location Bug Analysis

  1. Leaflet Map Size Invalidation Bug: When OrderSuccessModal.jsx opens, CSS animations (animate-scale) start with a zero-dimension container. Leaflet initializes before the modal reaches full size. Without calling map.invalidateSize(), tiles and markers render out of bounds.
  2. Mobile HTTP Security Restriction: navigator.geolocation.watchPosition in RiderPortal.jsx is strictly blocked by iOS Safari and Android Chrome over non-HTTPS connections. Testing over http://192.168.x.x:5173 results in silent permission failure.
  3. Hardcoded Fallback Mismatch: App.jsx falls back to riderLocations['rider-1']. If the order is unassigned or assigned to a different rider, the tracking screen shows the wrong rider or nothing.

4. Order Flow & Synchronization Issues

  • LocalStorage Cache Pollution: In App.jsx, orders are initially loaded from localStorage.getItem('unavu_ecosystem_orders'). If an order was modified or cancelled from another portal (e.g. Hotel or Rider), the customer device continues to display stale data until manual storage clearing.
  • Status State Machine Absence: An order can jump from PLACED straight to DELIVERED without verifying intermediate kitchen and rider handoff stages.
  • Doorstep Delivery OTP Validation: Delivery OTP verification must occur on the server via an atomic endpoint, not solely inside the frontend rider client.

5. Mobile Version Responsiveness Issues

  • Floating Elements Collision: MobileBottomNav is fixed at bottom: 0 with z-index: 999. On mobile screens, it covers the Cart checkout bar, active order tracker, and address selection footer.
  • Modal Height Overflow: The order success tracking modal contains a Header + Stepper + Leaflet Map + OTP Box + WhatsApp notice totaling over $680\text{px}$. On phones with $667\text{px}$ viewport height, the bottom buttons are pushed off screen.
  • iOS Safari Auto-Zoom: Inputs with font size under $16\text{px}$ trigger iOS auto-zoom, causing the entire layout to become horizontally misaligned.

7. Recommended Database Schema (PostgreSQL / MongoDB)

-- Orders Table with Geospatial Coordinates
CREATE TABLE orders (
    id VARCHAR(30) PRIMARY KEY, -- UNV-784102
    customer_id UUID REFERENCES users(id),
    customer_name VARCHAR(100) NOT NULL,
    customer_phone VARCHAR(20) NOT NULL,
    restaurant_id VARCHAR(50) NOT NULL,
    rider_id VARCHAR(50),
    status VARCHAR(30) DEFAULT 'PLACED', -- PLACED, PREPARING, READY_FOR_PICKUP, OUT_FOR_DELIVERY, DELIVERED
    delivery_address TEXT NOT NULL,
    delivery_lat NUMERIC(9, 6),
    delivery_lng NUMERIC(9, 6),
    delivery_otp VARCHAR(6) NOT NULL,
    grand_total NUMERIC(10, 2) NOT NULL,
    payment_method VARCHAR(20) DEFAULT 'UPI',
    payment_status VARCHAR(20) DEFAULT 'PAID',
    placed_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Riders Table with Real-Time Location
CREATE TABLE riders (
    id VARCHAR(50) PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    phone VARCHAR(20) NOT NULL,
    current_lat NUMERIC(9, 6),
    current_lng NUMERIC(9, 6),
    is_online BOOLEAN DEFAULT TRUE,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

8. Step-by-Step Remediation Roadmap

We are ready to fix each problem one by one in whatever order you prefer. Here is the recommended sequence:

  1. Step 1: Fix Rider Location & Live Map — Add map.invalidateSize(), sanitize coordinate updates, fix Leaflet marker updates, and enable resilient simulated / real GPS fallback.
  2. Step 2: Fix Mobile Layout & Overlaps — Fix MobileBottomNav collision with checkout buttons, convert modals to scrollable bottom sheets, and eliminate iOS auto-zoom.
  3. Step 3: Fix Order Lifecycle & State Synchronization — Remove conflicting localStorage overrides, ensure real-time multi-portal order status sync, and secure OTP verification.
  4. Step 4: Database Integration — Migrate from db.json to a robust database (PostgreSQL with Prisma or MongoDB) with Redis caching.
